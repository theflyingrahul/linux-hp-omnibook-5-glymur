# Headset: the 7.4 codec node, the jack and the left/right swap, November 21, 2026

What `-23` showed (`docs/runbook-results-23-2026-11-21.md`): the headset
plays and its microphone records on `SWR_MIC0`. Three things do not work:
- the left and right channels swap from one stream to the next;
- jack detection;
- the headset button.

## Linux 7.4 needs `qcom,sdca-compliant` (fixed in `-26`)

Qualcomm's 7.4 WCD9378 SDCA driver (`sound/soc/codecs/wcd9378-sdca.c`)
returns `-ENODEV` unless the codec's device-tree node has
`qcom,sdca-compliant`. The codec ID `0x0217:0x0110` also covers a non-SDCA
"mobile" variant, which a second driver (`wcd9378-sdw.c`) handles. The 7.4
binding's compatible is just `sdw20217011000`, and the Glymur CRD's node
carries the property.

Our node came from the 7.3 CRD and has neither. So on `-25`'s test tree the
SDCA driver would not bind, and the mobile driver may take the codec instead.
`-26` gives the node the 7.4 form. `-25` should not be used for headset
tests.

## Jack detection

`GE 35 Detected Mode` read `0` ("Jack Unplugged") with the headset in and
out, so the codec's detection never reports a plug. The repeated
`ASoC error (-16)` is a separate symptom:
- It is a read of `0x40c00908`: function 3 (SimpleJack), entity `0x12`
  (`SU 35`, the microphone selector), control 1 (its selector).
- Nothing on the SoundWire or SDCA read path returns `-EBUSY`. A regmap in
  cache-only mode does, for a register it has no cached value for. That is
  how a runtime-suspended SDCA function reads, and the driver gives SU 35's
  selector no reset value.

So the `-16` comes from reading the selector while the codec sleeps, not
from the jack.

Still open:
- the mic-bias supply: the CRD's is BOB1, ours is a dummy. BOB is on as the
  LDOs' parent, so this affects the microphone, not plug detection;
- HP's GpioInt on GPIO 193: the codec may report jack events on that line
  rather than in band. Nothing here uses it yet.

`-26`'s tree, with the SDCA driver bound on 7.4, is the first chance to see
whether detection behaves differently.

## The left/right swap

The same `left.wav`, through the same route, played left on some streams and
right on others. The headset's playback goes over `swr2`, which borrows
`swr1`'s data lanes 2 and 3 (`qcom,secondary-lanes`). 7.4's driver ties the
two controllers' frame generators with MM_SYNC, programmed at init and on
resume. No upstream change mentions a channel swap.

`check-headset.sh` (from `-26`) plays the left tone in six separate streams.
During each stream it reads both controllers' registers and the codec's
SoundWire registers (debugfs, read-only), then asks which side the tone
played on. It then lists the registers that are identical within each group
but differ between the "left" and the "right" streams:
- **some registers differ:** they name the block that starts out of step;
- **none differ:** the swap is upstream of SoundWire, in the codec DMA or
  the RX macro.
