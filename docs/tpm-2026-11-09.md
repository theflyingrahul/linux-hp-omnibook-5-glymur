# TPM: Which TPM Windows Uses, and the Next Evidence, November 9, 2026

Issue #19, continuing `docs/tpm-2026-11-06.md`. Read-only work on the
laptop's Windows (not elevated) and in HP's driver pack. Nothing was sent to
the TPM beyond Windows' own `tpmtool getdeviceinformation` query.

## Which TPM it is

`tpmtool getdeviceinformation` reports manufacturer `QCOM` (Qualcomm),
vendor string "xCG fTPM", firmware 4.0.0.1, TPM 2.0 (spec 1.62), PPI 1.3,
initialised and ready for storage and attestation, not locked out (lockout
counter 0, 32 tries, 7200 s interval). It also reports "Bitlocker PCR7
Binding State: Binding Not Possible": BitLocker on this laptop is not
sealed to Secure Boot's PCR 7, so it uses another PCR profile, which only
an elevated `manage-bde -protectors -get C: -Type TPM` shows.

Windows enumerates three security devices:

| Device | Instance | Driver |
|---|---|---|
| Trusted Platform Module 2.0 | `{36DEAA79-…}\TREETPM` under the TrEE secure-service bus | Microsoft `tpm.inf` |
| Microsoft Pluton security processor | `ROOT\PLUTONQC` | Microsoft `PlutonQc.inf` |
| Qualcomm Secure Processor (SPU) | `ACPI\QCOM0F87`, `ACPI\QCOM0F8D` | Qualcomm `qcsp` |

So the TPM that BitLocker and Windows use is Qualcomm's firmware TPM in
TrustZone (`qcom.tz.tpm`), not Pluton. Pluton is the secure processor's own
service: the SPU driver (`qcsp_8480`) loads the NVM apps `sp_nvm`,
`stpm_lite_msft` and `ksp_msft` and keeps its data in
`C:\Windows\ServiceState\qcsp_8480\Data`.

## What the TrEE driver's INF says

`QcTrEE8480.inf` (HP's pack, driver 685.13804) defines each TrustZone
service with the host-side services it needs (`OSDependencies`):

| Service | App | OSDependencies |
|---|---|---|
| UEFI variables | (built in) | RPMB OS service `{27447C21-…}` |
| WinSecApp | `qcom.tz.winsecapp` | RPMB OS service |
| Pass-through, inline crypto | (built in) | RPMB OS service |
| **TPM** | **`qcom.tz.tpm`** (resident, `LoadApp=0`) | **none** |
| MSSecApp, manufacturing mode | `qcom.tz.mssecapp`, `qcom.tz.mfgmodemgmt` | none |

The driver's file listener is on (`FSListener=1`, `FileListenerPath =
\DriverData`, which is `C:\Windows\System32\drivers\DriverData`), its
SFS listener wait is 2 s, and the TPM transfer timeout 5 s.

Two consequences:

- The TPM service declares no dependency on the RPMB service, while the
  UEFI-variable service does. Linux already writes UEFI variables through
  the same secure world with no RPMB listener at all (QSEECOM
  uefisecapp; on many Snapdragon X laptops those writes persist). Kernel
  `-20`'s `check-efivars-write.sh` measures that here: a variable written
  from Linux, checked after a reboot. If it survives, the secure world
  keeps a service's storage without Linux serving its listeners, which
  weakens the 2026-11-06 concern for the TPM.
- The driver's TPM code still signals "RPMB listener up" to the TPM app
  (2026-11-06 static analysis), and the file listener stays a candidate.
  The INF alone does not rule them out.

## The next evidence (elevated, read-only)

`scripts/windows/tpm-storage-evidence.ps1`, run once from an elevated
PowerShell, collects what this session could not read (it is not
elevated):

- BitLocker's TPM protector and its PCR profile (no recovery password);
- names, sizes and times of the files in `drivers\DriverData` and in the
  SPU's data folder, before and after one read-only TPM query (the
  endorsement key's public part, which the TPM reads from its
  non-volatile storage);
- a trace of the TrEE driver's WPP provider
  (`{DE3B1201-A1DF-478A-9062-E443CDABF070}`, the one its autologger
  enables) during that query. HP's pack has no symbols for the driver, so
  the trace gives event timing and IDs, not messages.

A file under `DriverData` that changes with a TPM read would put the TPM's
state on the BitLocker volume, out of Linux's reach: Linux then sends the
TPM nothing. No change there, together with a surviving UEFI write from
Linux, would make a read-only Linux TPM test (Qualcomm's driver, version
query and PCR reads only) the next step, still with the owner's go-ahead
and still without `TPM2_Clear`, NV writes or `systemd-cryptenroll`.

## Not changed

No TPM driver in `-20`. Qualcomm's posted driver also needs QTEE service
81, which HP's firmware does not implement (the `-18` log), so it would not
bind anyway; Windows reaches the app by name through QSEECOM, which the
posted driver does not do.
