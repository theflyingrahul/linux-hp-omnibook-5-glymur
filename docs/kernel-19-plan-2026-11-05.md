# Kernel -19 plan, November 5, 2026

What `-18` showed (`docs/runbook-results-18-2026-11-05.md`), what upstream
added since, and what `-19` changes. The patch list and its sources are in
`patches/README.md` ("Base move for `-19`").

## Where `-18` left things

- Input works on the rc6 base, the boot-time `CMD timeout` is gone, and F9
  arrives from the EC as `KEY_MICMUTE`.
- No audio DSP stall in three boots (about 4 and 24 minutes, and at least
  12) and three WirePlumber restarts. `-17` stalled at 815 s, so the bisect
  of `backports/0038–0039` is not settled; it needs one long session.
- Not run: charging unplug and replug, a USB device in each port, the power
  button.

## The new base

qcom-next was rebuilt on Linux 7.3 (`17bbb4b37bbc`, `qcom-next-7.3-20261031`).
It carries eight of our backports itself and brings the rest of Qualcomm's
A8x GPU vote series. Two of our own fixes, the wsa884x runtime-PM fix and
the topology size fix, went into 7.4-rc1 through Qualcomm developers in the
same form, so they are carried in mainline's form and need no sending. 25
accepted fixes from 7.4-rc1 and linux-next are taken, mostly audio
(q6apm buffer unmapping, GPR clean-up, SoundWire interrupt before clock
gating, wsa884x), plus clocks, display, USB-C, SPMI, PCIe and Wi-Fi.

Two base changes bear on the `-17` freezes, where a stalled DSP held the
clock prepare lock: Qualcomm's LPASS macros now manage their clocks in
runtime PM (FROMLIST, in the base), and the rcg2 force-enable fixes
(`backports/0060–0061`). Neither is a known fix for the stall.

## The headset jack (issue #4)

On 2026-10-17 the WCD9378 (`MAN_0217 PART_0110`) waited on unposted LPASS
patches (`docs/audio-headset-path-2026-10-17.md`). The new base has all of
them: the WCD9378 SDCA codec driver (FROMLIST), the Glymur LPASS and LPASS
audio clock controllers (PENDING), SoundWire multi-lane support (PENDING),
LPASS codec v2.9, and the RX/TX macro, `swr1` and `swr2` nodes in
`glymur.dtsi`. Its own Glymur CRD board file (`glymur-crd.dtsi`) wires the
codec, and HP's Windows drivers run the CRD's audio configuration.

`-19`'s test device tree follows the CRD:

| Item | Value | Source |
|---|---|---|
| bus | `swr2` master, `swr1` its data lanes 2 and 3 (`qcom,secondary-lanes`) | CRD; HP's `QSJ0` maps four lanes |
| data ports | 2 capture; 6, 7, 8 playback; the CRD's per-port arrays | CRD; HP's `QSJ0` lists the same ports |
| codec | `qcom,wcd9378c`, unique ID 3 | CRD; HP's `_ADR` does not give the ID |
| reset | TLMM GPIO 191, active low | HP's DSDT `ASCD` |
| `vdd-buck`, `vdd-rxtx` | L15B 1.8 V | HP's `ACDResources.bin`, `ASCDResources.bin` |
| `vdd-io` | L18B 1.2 V | CRD; held on for the amplifiers already |
| `vdd-mic-bias` | not described (dummy) | the CRD's BOB1 has no HP evidence |
| sound card | `WCD Playback` on `RX_CODEC_DMA_RX_0`, `WCD Capture` on `TX_CODEC_DMA_TX_3`, the CRD's two DAPM routes | CRD |

Not described: HP's `GpioInt` on GPIO 193 (the SDCA codec reports jack
events in band) and HP's `GpioIo` pin 2. GPIO 191 joins the test tree's
allow-list; the DTB passes `check-dt-gpio-allowlist.py`.

The kernel config adds `SND_SOC_SDCA`, `SND_SOC_SDCA_CLASS` and
`SND_SOC_WCD9378_SDCA` (modules). The topology (both variants) adds the
headset playback and capture graphs as `X1E80100-CRD.m4` has them: the
headset shares `MultiMedia1` and `MultiMedia2` with the speakers and the
built-in microphones, selected by the DSP mixers. There is no UCM for the
headset yet: the SDCA driver's control names are only known once it runs.
`check-headset.sh` collects them, plays a quiet tone and records from the
headset microphone by switching the DSP mixers by hand, and puts them back.
The UCM headset devices follow from that log.

Risk: the headset path is new code on the same DSP and clock path as the
`-17` stall. The speaker and microphone path is unchanged. The long audio
session that settles the stall question should therefore run on `-18`,
which is installed now, before `-19` goes in.

## The RTC, the crypto engine and the RNG: drivers exist, they were off

All three were absent on `-18`, and none needs new code. The base has
the drivers. The RTC and RNG drivers were not in our configuration; the
crypto algorithm driver was (`CRYPTO_DEV_QCE=m` from Ubuntu's config) but
nothing bound the node on `-18`, and on the new base the node belongs to the
new core driver instead.

- **RTC** (issue #17). Windows reads the time through the ADSP's PMIC GLink
  RTC service (`\_SB.PRTC._GRT`). qcom-next carries Qualcomm's driver for
  exactly that ("FROMLIST: rtc: qcom: rtc-glink: Add PMIC GLINK RTC driver
  and extend pmic_glink", Raj Aryan and Kamal Wadhwa, posted 2026-08-07),
  and the Glymur `pmic_glink` data already asks for the RTC client, which is
  why `pmic_glink.rtc-glink` appeared without a driver. It reads only,
  unless the `pmic-glink` node sets `allow-set-time`, which it does not
  here. `CONFIG_RTC_DRV_QCOM_GLINK=m`.
- **Crypto engine** (`crypto@1dfa000`, `qcom,glymur-qce`). The base has
  Qualcomm's whole rework, accepted into the crypto tree (in linux-next):
  the new core driver and auxiliary bus (Bartosz Golaszewski), runtime PM
  and interconnect bandwidth scaling (Udit Tiwari, tested by Pankaj Patil),
  and algorithms registered only on request, because the engine is slower
  than the CPU's own crypto instructions and races with the secure world.
  With nothing bound, the interconnect never finished `sync_state` and kept
  its boot-time bandwidth votes. `CONFIG_QCOM_CRYPTO_CORE=m` only: the core
  driver binds the node, holds the memory interconnect path and drops its
  vote under runtime PM, which is all `-19` needs. The algorithm driver
  (`CONFIG_CRYPTO_DEV_QCE`) stays off, because qcom-next `17bbb4b37bbc`'s
  `drivers/crypto/qce/core.c` does not compile: its merge of the
  auxiliary-bus conversion with the runtime-PM change declares `res` twice
  in `qce_crypto_probe()`. It would register no algorithms by default
  anyway.
- **TRNG** (`rng@10c3000`, `qcom,glymur-trng`, already in the upstream
  binding): `qcom-rng` matches `qcom,trng`. `CONFIG_HW_RANDOM_QCOM=m`. The
  CPU's own random-number instructions were already in use.

## The Mahua video trials

From the Windows analysis (`docs/video-iris-windows-2026-11-06.md`):
`glymur-bringup/0004` adds two default-off parameters to the `-17`
diagnostics, `diag_hw_core` (the hardware core whose status, bridge reset
and NOC handshake bits vcodec 0 uses) and `diag_pwr_ctl` (clear the
wrapper's core power control register once in hardware mode, wait for the
core's power status, log both). A new DTB, `-test-iris`, is the test tree
with Iris on, chosen at the GRUB menu for one boot, and `check-video.sh
--mahua` runs four trials: one core (`mvs0`), core ID 2, hardware core 1,
power release; then without the release, without the core-1 bits, and with
2 pipes. No search found anyone else's work on Mahua video; the encoding
follows Qualcomm's downstream socinfo sub-part handling.

## USB full and low speed (issue #6)

Every port has run high speed and SuperSpeed since `-6`, but full- and
low-speed devices (mice, keyboard receivers) plugged straight in fail with
`error -71`. All ports use the M31 eUSB2 PHY, which needs a repeater to
signal full and low speed at the connector. HP's PEP tables vote two rails
for every USB port and for nothing else: LDO15_B at 1.8 V and LDO7_B at
3.072 V (the repeaters' `vdd18` and `vdd3`; the CRD runs LDO7_B at
2.79 V). The test tree declared the USB-C SMB2370 repeaters without
supplies and LDO7_B not at all, so nothing in Linux held the 3 V side on.
`-19`'s test tree declares LDO7_B at HP's 3.072 V, always on (shared by
all ports), and gives both repeaters `vdd18` and `vdd3`. Added after the
kernel build, as a device-tree-only change: the two test DTBs were rebuilt
in the `-19` tree and the package repacked (`67a8bb32…`, replacing the
build's `3df1db5b…`; the daily and minimal DTBs are unchanged).

## Also in `-19`

Qualcomm's Glymur SoC device-tree fixes from the laptops tree
(`backports/0072–0075`): USB PHY interrupts, the HS-only (camera) USB
controller at its rated clock, PCIe `t-power-on-us`, idle-state names.

## Not in `-19`

- External displays: the laptops tree's Glymur DP PHY series is proposed,
  not accepted, and reprograms the PHY that carries USB-C SuperSpeed.
- Iris: nothing new upstream for this die. Two findings of 2026-11-05:
  - Making `video_cc_mvs1_gdsc` a child of `mvs0c` would change nothing:
    the VPU 3.6 code powers the controller domain (`mvs0c`) before either
    core, so `mvs0c` is already on when `mvs1` fails to come up.
  - Qualcomm's own `mahua.dtsi` deletes the second video core's thermal
    zone (`/delete-node/ &thermal_video_1;`) and moves `thermal_video_0`
    to another sensor: Mahua has one video core. That fits `mvs1` never
    powering on. What is left is which core ID and pipe count the
    firmware wants for that one core; `-17`'s trials found only core ID 2
    accepted, and the session then stalled. HP's PEP tables have no video
    footswitches (Windows' Adreno kernel driver powers video itself), so
    the answer is in `qcdxkm8480.sys`.
- Boot options: the runbook's part D boots once without Ubuntu's generic
  `clk_ignore_unused pd_ignore_unused arm64.nopauth`, edited at the GRUB
  menu, with no change on the USB.
- RTC, suspend, TPM: nothing new upstream.
- F11 and the Copilot key: both arrive as the chords HP's firmware sends
  (Ctrl+F17, Meta+Shift+F23); a hwdb rule cannot undo a chord, and these
  keys stand for no Linux action, so a GNOME custom shortcut is the place
  for them.
