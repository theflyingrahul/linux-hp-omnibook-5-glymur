# Kernel -16: the four open problems from -15, October 21, 2026

What the `-15` boots left open (`docs/runbook-results-2026-10-21.md`,
`docs/audio-speakers-down-2026-10-21.md`), what was found by reading the
kernel trees and HP's evidence, and what `-16` changes. Nothing here has
been booted yet. qcom-next is unchanged (`1a0586064ee1`, tag
`qcom-next-7.3-rc4-20261014`); mainline (`v7.3-1703-ga804c5742b`) has no
new commit in our drivers since the `-13` check that applies.

| Problem | Cause | `-16` |
|---|---|---|
| EC does not bind (no F9, mute LEDs, skin temperature) | Thermal zone name over 19 characters | Zones renamed in the test device tree (fixed, certain) |
| Speakers drop off the SoundWire bus | Not known. The test device tree gives the amplifiers dummy supplies | L15B and L18B declared and wired (hypothesis) and a watcher to find the trigger |
| Iris video: `video_cc_mvs1_gdsc` stuck off | The Glymur platform data powers two video cores; Mahua has one (probable) | `qcom,mahua-iris`, one core (`upstream/qcom-next/0008`) |
| External display: EDID failure, then a hang | Not fully known (below) | DisplayPort off again in the test device tree; nothing to plug into until it is understood |

## 1. EC thermal zone names

`thermal_zone_device_register()` refuses names of 20 or more characters.
`ec-thermistor-1-thermal` is 23, so the EC driver's hwmon registration
failed with `-22` and took the whole probe with it. The four zones are
`ec-therm1-thermal` … `ec-therm4-thermal` (17 characters), already in
`dts/qcom/mahua-hp-omnibook-5-bf1xxx-test.dts` and
`docs/thermal-skin-2026-10-20.md`. Everything that waited on the EC
(F9's own event, the mute LEDs, the EC interrupt, the skin-temperature
trips) is untested until `-16` boots; `docs/linux-runbook-2026-10-20.md`
steps 4 and 9 still apply.

## 2. Speakers leaving the bus

What is known, from `docs/audio-speakers-down-2026-10-21.md`: both
WSA884x amplifiers attach after boot, play, then show `UNATTACHED`; each
time a `SWR bus clsh detected` line comes first (on the first `-15` boot
at 15:52:26, on the second at 20:07:14), and they do not come back. The
shared reset line reads asserted afterwards. The microphones (VA macro)
are unaffected.

What is new: the kernel log says
`wsa884x-codec …: supply vdd-io not found, using dummy regulator` and the
same for `vdd-1p8`, so Linux holds neither of the amplifiers' rails. All
four Glymur and Mahua laptop device trees in the Linux MSM laptops tree
that have these amplifiers (the CRD, ASUS Zenbook A14, HP EliteBook X G2q,
ThinkPad T14s Gen 7) give them `vdd-1p8-supply` (L15B 1.8 V) and
`vdd-io-supply` (L18B 1.2 V). HP's own evidence for the two rails:

| Rail | Voltage | HP evidence |
|---|---|---|
| L15B | 1.8 V | `ACDResources.bin` and `ASCDResources.bin` (the audio devices), and the USB ports' PEP votes |
| L18B | 1.2 V | `\_SB.GPU0` (the display) and `\_SB.SDC2`; not an audio vote, but the same voltage the references use |

`-16`'s test device tree declares both on PMH0101 (`B_E0`) as always-on,
at those voltages, HPM mode (as `lab-rails.dtso` does for the display's
rails) and wires them to both amplifiers. They are shared (L15B feeds the
USB PHYs and eUSB2 repeaters, L18B the display), which is why they are
always-on and not requested. Whether this is the cause is not known: it
is the one difference from every reference board that touches the
amplifiers' power, and a rail that nothing in Linux votes for can change
state behind the driver's back. If the amplifiers still leave the bus,
the rail is ruled out and the next suspects are the SoundWire master's
runtime-PM clock stop (`qcom_swrm_runtime_resume()` re-enables the clash
interrupt as it leaves clock stop) and the shared reset line.

`scripts/linux/glymur-ssd/watch-audio.sh` is for that case: it logs the
amplifiers' status and runtime-PM state, the master's, and both rails'
state, with a dump and the SoundWire driver's debug messages at each
change, so the trigger can be matched to a time. Run it from the
first minute of the session and leave it.

Not done: the upstream gap in `qcom-soundwire` (a slave that left the bus
during a clash is not re-enumerated) needs the trigger first.

## 3. Iris video: `video_cc_mvs1_gdsc`

`-15` on the test device tree: the first core powers on, the second does
not (`video_cc_mvs1_gdsc status stuck at 'off'`, a `gdsc_toggle_logic`
warning, then `power on failed`) on every open of the video node (the
V4L2 probe at login, `v4l_id`, the test clip). The power-on loop in
`iris_vpu36_power_on_hw()` runs over `num_cores`, which Glymur's platform
data sets to 2.

Why a second core is not expected here:

- `mahua.dtsi` deletes `thermal_video_1` and keeps `thermal_video_0`, as it
  drops the second CPU cluster, the QMX2 cluster, one PCIe controller and
  two TSENS blocks;
- qcom-next has no Mahua-specific video compatible or node: `mahua.dtsi`
  leaves the Glymur iris node alone and the Mahua CRD runs it unchanged;
- the evidence on this laptop is the stuck GDSC itself. Neither HP's DSDT
  (only `EVA0`, `QCOM0FD7`, no Iris device) nor the firmware strings say how
  many cores exist: `qcvss8480.mbn` handles core 0 and core 1 alike.

So this is probable, not proven. `upstream/qcom-next/0008` adds
`qcom,mahua-iris` (fallback `qcom,glymur-iris`, as for Nord) with the
Glymur platform data and `num_cores = 1`, and the binding allows the new
compatible. The shared node still describes the second core's clocks, OPP
column, resets and power domain, so the tables are left alone and the
unused core's clocks are never requested. The test device tree uses it.
If the first core also fails, or the second core was only waiting on
something the first one needed (its GDSC has no parent here, where
`video_cc_mvs0_gdsc` has `video_cc_mvs0c_gdsc`), the log will say so: look
for `mvs0` in the same lines. The patch is not for upstream until it is
known that Mahua really has one core; Qualcomm's Iris owners can say.

## 4. External display

The chain on `-15` (`captures/2026-10-21-runbook/display-hotplug-crash.txt`):

1. a Cypress Billboard device (`04b4:5210`) appears on the hinge-side
   port: the adapter or monitor did not enter DisplayPort alt mode;
2. `msm_dp_display_process_hpd_high`: the DPCD read worked, the EDID read
   failed twice (`panel edid read failed`), and the function carries on,
   because the failure is not an unplug;
3. `msm_dp_bridge_get_modes` returns 0. DRM's probe helper normally adds
   fallback modes for a connected connector without an EDID, which would
   give the compositor something to light (not confirmed: this boot had
   no `drm.debug`);
4. `msm_dp_display_atomic_pre_enable`: `DP display prepare failed,
   rc=-107`;
5. the display controller, already committed to the encoder, reports
   `vblank timeout` and `frame done timeout` every 50 ms for 12 s, then
   the machine resets with no oops. Another Glymur laptop (ASUS Zenbook
   A16, `e249a6e2a1`) saw the same kind of silent reset from the DP
   disable path after a failed enable and fixed it; that commit is in our
   base already (`msm_dp_display_atomic_disable()` returns early when
   `power_on` is false), so this is another path to the same cliff.

The step 2 failure is a link or AUX problem, not a software one: no DP
alt mode, and an AUX channel that answers DPCD but not the EDID. Qualcomm
has a series for the Glymur DP PHY (11 patches by Ritesh Kumar, v5,
`20261001-glymur-phy-v3-v5-*`, applied by Abel Vesa; the Linux MSM
laptops tree carries it, qcom-next and mainline do not). qcom-next
already has older revisions of the first three patches and some of the
rest ("Rework DP PHY runtime configuration" and the register-header
patches), and the two versions do not merge: a three-way merge of the
series' net change into our `phy-qcom-qmp-combo.c` gives 20 conflicts
that are not mechanical, and in the one place both sides can be compared
(`qmp_v8_dp_aux_init()`) they are identical. The differences that remain
in the Glymur v8 path are `QSERDES_DP_PHY_CFG_1` (`0x0f` here, `0x2f` in
the series), the per-link-rate auxless, silence and LFPS values and drive
levels (fixed values here), the CLKBUF enable writes, and
`dp_mode_ignore_reverse`. The same PHY carries USB-C SuperSpeed, which
works now, so a blind port is not worth the risk of breaking it. It stays
a candidate for after Qualcomm's newest revision is on the list or in
qcom-next (`patches/README.md` records the fetch).

`-16` therefore does not enable DisplayPort in the test device tree
(`&mdss_dp0` and `&mdss_dp1` are disabled in `glymur.dtsi`); a monitor on
the USB-C ports gets USB only. The next step needs hardware with DP
debugging on: boot the `-15`-style tree again only when the owner is
ready for a reset, with `drm.debug=0x102` on the command line and
`check-display.sh` run before the plug, so the alt-mode and AUX messages
(`ff01`, SVID) reach the log.

## What to check on the `-16` boot

1. `dmesg | grep -i "thermal zone\|hp-omnibook-5-ec"`: no `-22`; the EC
   hwmon, `ec-therm1-thermal` … `ec-therm4-thermal`, the LEDs and the EC
   interrupt exist (runbook steps 4 and 9).
2. Speakers: `sudo bash watch-audio.sh` from login, then `check-audio.sh`;
   the amplifiers' `vdd-io`/`vdd-1p8` lines should be gone from the log.
3. Video: `sudo bash check-video.sh`; no `video_cc_mvs1_gdsc` line; if it
   fails, the first line naming a power domain.
4. Do not plug a monitor.
