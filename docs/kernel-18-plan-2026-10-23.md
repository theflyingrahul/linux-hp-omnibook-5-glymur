# Kernel -18 plan, October 23, 2026

What `-17` showed (`docs/runbook-results-17-2026-10-23.md`), what others report
about the same symptoms, and what `-18` changes. The side project's plymouth
theme and services stay off the laptop's boot path for now (the owner,
2026-10-23).

## The audio DSP stall

On `-17` the ADSP stopped answering APM and PRM commands twice
(`CMD timeout for [1001004]` and on), and a 5 s synchronous LPASS clock vote
under the clock framework's global prepare lock turned each stall into a
system-wide freeze.

- **New in `-17`.** Every log from earlier kernels shows only the boot-time
  `[1001021]` timeout (`-14`'s crash aside); the `1001004`/`1001003`/`1001010`/
  `100100f` cascade appears first on `-17`.
- **SoundWire parity errors come first.** No earlier kernel logged a WSA884x
  `Parity error detected`. On `-17` they came 29 s (boot 1) and 5 s (boot 2,
  both amplifiers, right at a WirePlumber restart) before the stall. The
  amplifier reports it received corrupted frames, a link-level problem.
- **Online.** Nothing matches this cascade on other Snapdragon X laptops.
  Parity errors elsewhere are a sign of link instability (for example after
  resume, [fwupd/firmware-lenovo#632](https://github.com/fwupd/firmware-lenovo/issues/632);
  spurious ones at start-up were filtered in 2020,
  [soundwire parity filtering](https://lkml.iu.edu/hypermail/linux/kernel/2009.1/01171.html)).
  `CMD timeout` at boot is reported as harmless on other X laptops
  ([jglathe/linux_ms_dev_kit#94](https://github.com/jglathe/linux_ms_dev_kit/issues/94)).
- **The boot-time timeout has a known cause.** Qualcomm traced DSP command
  timeouts to GPR publishing a service's callback only after the client probe
  returns, so early replies are dropped
  ([qualcomm-linux/kernel#1321](https://github.com/qualcomm-linux/kernel/issues/1321)).
  The fix, "soc: qcom: apr: Publish GPR callback before client probe" and
  "ASoC: qcom: q6apm: Guard callbacks until probe data is ready" (FROMLIST,
  [kernel-topics PR 2092](https://github.com/qualcomm-linux/kernel-topics/pull/2092)),
  is in the new qcom-next base. It explains the `[1001021]` timeout at about
  9.7 s in every boot, not the runtime stall.

The audio code new in `-17` is `backports/0037–0039` (q6apm) and `0008`
(topology; a no-op with the plain topology). `0039` resets the hardware
pointer on every prepare, which a session restart triggers, and `0038`
changes the reported position. **`-18` drops `0038` and `0039`** as a bisect
step; `0037` (a removal path) stays. If the stall is gone, they come back one
at a time; if not, they were not the cause.

The 5 s vote under the global clock lock is worth raising upstream either
way: a DSP that does not answer should not stall the GPU and the I2C input
devices. That needs a reproducible case first.

## The WirePlumber session stall

WirePlumber's v4l2 monitor blocked its event queue while opening the Iris
decoder timed out. Disabling the Iris nodes by rule did not help, which
matches a known WirePlumber 0.5.17 bug: `create-device.lua` returns without
`transition:advance()` for a disabled v4l2 device and wedges the event queue,
leaving the card on profile "off" with only "Dummy Output"
([omacom/omarchy#12720](https://github.com/omacom/omarchy/issues/12720)).

**`-18` turns Iris off again** in the test device tree, so there is no video
node for the monitor to block on, and the workaround that disabled the whole
v4l2 monitor (`52-no-v4l2-monitor.conf`) goes.

## Iris

With `diag_core_id=2` the firmware stopped refusing the session; with mask 1
it refuses as before. Mask 2 is the second core, whose GDSC
(`video_cc_mvs1_gdsc`) never turns on. The next question is why that GDSC
stays off on Mahua; nothing online covers Glymur or Mahua here (the nearest
are GDSC hardware-control fixes on other SoCs, such as the X13s venus fix
behind CVE-2024-50266). The diagnostics (`glymur-bringup/0003`) stay for that
work.

## The RTC

HP's firmware has no `RTCInfo` variable (98 variables read on `-17`, none
time-related), so `qcom,uefi-rtc-info` fails with `-ENOENT`. HP's ACPI shows
how Windows gets the time: the time-and-alarm device `\_SB.PRTC` (`ACPI000E`)
reads it in `_GRT` through PMIC GLink (`\_SB.PMGK`, fields `XRT*`), from the
ADSP's PMIC service. **`-18` turns the RTC node off**; a PMIC GLink time
client would be new work (issue #17). The PMK8850 PMIC stays in the test tree
for the power key.

## The new qcom-next base

qcom-next moved to `c7896917e523` (tag `qcom-next-7.3-rc6-20261023`, 1869
commits since `1a0586064ee1`). It carries `backports/0018`, `0019`, `0021`
and the GPR race fix above. It also carries `cb97bf3d4f` ("i2c: qcom-geni:
Fix hardcoded clock index in SE_GENI_CLK_SEL") without mainline's follow-up
`8cb5c17be3` ("Restore the source-clock selection policy", Abel Vesa), which
fixes I2C HID keyboard and touchpad failures that `cb97bf3d4f` caused on the
X1E80100 CRD. `-18` carries `8cb5c17be3` as `backports/0046`. Device-tree
I2C now needs an exact 19.2 MHz level in the QUP clocks' DFS table; `-17`'s
boot report shows 19.2 MHz in use on several QUP clocks, so it is expected to
be there, and the keyboard is the first thing to check on `-18`.
