# Embedded Controller on the Device-Tree Boot: September 30, 2026

The EC (fan, EC thermistors, keyboard backlight, HP hotkey plumbing) was
reachable only on the ACPI boot, where HP's AML drives it over `IC10`
(`docs/cpuidle-and-ec-bus-results-2026-09-26.md`). No device-tree boot
describes it, so none has fan speed or EC temperatures
(`docs/status.md`). This note derives the EC's command set from HP's
ACPI tables (read-only work on the private DSDT/SSDT in `.work/`) and adds
a driver and a DT node for kernel `-9`. Nothing here has run on the
laptop yet.

## Bus

| Fact | Value | Source |
|---|---|---|
| Controller | `\_SB.IC10`, QUP 1 SE 1 at `0xa84000` = DT `i2c9` | DSDT `IC10` `_CRS`, `glymur.dtsi` |
| EC address, speed | `0x76`, 400 kHz, 7-bit | `I2cSerialBusV2` connections `ECIC` (SSDT) and `UMPC` (DSDT) |
| Pins | GPIO 36/37, function 1, pull-up | `IC10` PEP entry (`TLMMGPIO`), = `qup_i2c9_data_clk` |
| Clock | `gcc_qupv3_wrap1_s1_clk` | `IC10` PEP entry |
| Transfer mode | GSI (GPI DMA), FIFO disabled by firmware | ACPI boot, 2026-09-26; DT `i2c9` uses `gpi_dma1` |
| Event line | `ECGE` (`ACPI0013` GED) GpioInt, GPIO 66 | DSDT `ECGE` |

## Two command sets on the same address

1. **Qualcomm's reference EC commands** (AML field `DVUM`): `0x05` (read
   the pending event, as in `qcom-hamoa-ec.c`), `0x20`–`0x37`, `0x43`
   ("who am I"), `0x44` (capabilities, 6 bytes). HP's AML defines neither
   `0x0e` (firmware version) nor `0x42` (thermal capabilities), which
   `qcom-hamoa-ec.c` needs at probe, and that driver exposes no fan speed
   or temperatures. It is not used.
2. **HP's mailbox** (AML field `ICCR`, method `HQEX`), which carries the
   fan, thermistors and keyboard backlight:
    1. read status (`0xef`, 1 byte) until `0x00`, at most 20 × 5 ms;
    2. for commands with a payload, write it to `0xee` (32 bytes);
    3. write the command and sub-command to `0xed` (2 bytes);
    4. read status until `0xe0`, at most 20 × 5 ms;
    5. for commands with a reply, read 32 bytes from `0xee`.

   Each register access is a plain I²C write of the register byte plus
   data, or a write of the register byte and a repeated-start read, as
   the GenericSerialBus `AttribBytes` access defines it.

## Commands used by the driver

| Function | Command, sub-command | Reply | HP's AML |
|---|---|---|---|
| Fan speed | `0xbc`, `0x03` | bytes 0–1, little-endian RPM | `FAN1._FST` |
| Thermistor 1–4 | `0x26`, `0x00` / `0x07` / `0x04` / `0x0a` | byte 0, °C; `0xff` = no reading | `TRFE`, via `IC10._DSM` function 6, `TZ31`–`TZ34._TMP` |
| Keyboard backlight level | `0x05`, `0xff` | byte 0, level 0–2 | `WMID._WED` event `0x0d` |
| Set keyboard backlight | `0x05`, level 0–2 | none | `WMID.SBKT` (HP WMI keyboard backlight) |
| Mute LEDs, read | `0x06`, `0xff` | byte 1: bit 0 = LED 8, bit 1 = LED 9 | `WMID.GMLS` (HP WMI command `0x61`) |
| Mute LED on or off | `0x01`, `0x84`, then `0x06`, `0x08`/`0x09` (+`0x80` for on) | none | `WMID.SMLS` (HP WMI command `0x61`) |

Notes:
- `TZ35`–`TZ37` (thermistors 5–7, sub-commands `0x03`, `0x02`, `0x06`)
  return `_STA` 0 on this laptop, so the driver leaves them out.
- The thermal zones name the thermistors only "EC thermistor 1" to "4";
  their locations are unknown, so the driver uses those names.
- HP's `_TMP` reports the byte × 10 plus 2730 in tenths of kelvin; Linux
  converts with 2732, which is why the ACPI boot showed 40.8 °C for a
  41 °C reading.
- The keyboard has a backlight with two brightness levels (the owner,
  2026-09-30), matching EC levels 0 (off), 1 and 2. Its Fn key and
  auto-off timer already work without the OS, run by the EC
  (`docs/keyboard-hotkeys-2026-09-29.md`).
- The F6 (speaker mute) and F9 (mic mute) key LEDs have no bit in the
  keyboard's HID LED map (`docs/keyboard-hotkeys-2026-09-29.md`). HP's
  mute-LED WMI methods drive them through the EC as LEDs 8 and 9, sending
  the OS flag `0x84` first each time. Which LED is which is not in the
  tables: the driver names 8 `platform::mute` and 9 `platform::micmute`
  as a hypothesis, and `check-ec.sh` asks which key lights. Both keys send
  the same HID Mute usage, so telling them apart in software would need
  the EC's event path, which the driver does not use yet.
- Commands deliberately not used: fan trip points (`0xbd`), thermal
  thresholds (`0x28`), the other OS-state flags (`0x01`), and the reference
  fan-override command (`0x30`). They change how the EC runs the fan.

## What kernel `-9` adds

- `patches/kernel/upstream/qcom-next/0004`: DT binding
  `hp,omnibook-5-16-bf1xxx-ec`.
- `patches/kernel/upstream/qcom-next/0005`: `hp-omnibook-5-ec` driver
  (`CONFIG_EC_HP_OMNIBOOK5=m`). At probe it reads the fan speed once and
  fails if the EC does not answer. It registers:
    - hwmon `hp_omnibook_ec`: `fan1_input` and `temp1`–`temp4`, read-only;
    - LED `hp::kbd_backlight`, brightness 0–2.
    - LEDs `platform::mute` and `platform::micmute` (EC LEDs 8 and 9),
      without a default trigger until the test says which is which.

  It sends no command beyond the table above, polls instead of using the
  event line, and leaves the fan to the EC.
- The USB-test DT (`-usb.dts`, the "GPU and USB-A test" GRUB entry)
  enables `i2c9` with the EC node and unreserves GPIO 36/37. The other DTs
  are unchanged.
- `scripts/linux/glymur-ssd/check-ec.sh` reports the result. It steps the
  keyboard backlight through its levels and lights each mute LED in
  turn, asking what is lit. If the driver
  did not bind, it repeats only the read commands above with
  `i2ctransfer` (including the mute LED state), plus the reference `0x43`
  and `0x44` reads that HP's AML uses.

## Safety valve

The driver is a module. If the EC bus misbehaves, boot with
`module_blacklist=hp_omnibook_5_ec`, or use the other DT entries, which do
not enable `i2c9`.

## First live test, September 30: fan/thermal good, backlight write doesn't stick, LED 8 lights both keys

Booted, driver bound cleanly (`hp-omnibook-5-ec` on `9-0076`), `sudo bash
~/check-ec.sh` (`captures/2026-09-30-ec/ec-test-021459.txt`).

**Fan and thermistors: working as designed.** Five samples, 2 s apart,
all stable and plausible: `fan1 0 rpm` (idle, fan off, consistent with
the low-30s °C readings), thermistors 1–4 at 35/36/36/31 °C. This is real
data — the reverse-engineered `0xbc`/`0x26` mailbox commands work exactly
as HP's own AML uses them.

**Keyboard backlight: the write doesn't take.** All three levels (0, 1,
2) were set; the read-back was `0` every time, and the owner confirmed
the backlight was visibly off for all three, not just misreported. The
read and set commands go through different HP WMI methods (`_WED`
event 0x0d` to read, `SBKT` to set) — worth checking against the mute-LED
finding below before assuming the command table itself is wrong.

**Mute LEDs: real, but not a clean 1:1 mapping.** `platform::micmute`
(EC LED 9) is confirmed correct — turning it on lit only F9's LED, off
turned it off. **`platform::mute` (EC LED 8) is not F6-only: turning it
on lit *both* F6 and F9's LEDs together.** That's new, concrete evidence
against the driver's own labeling hypothesis for LED 8 — it isn't simply
"the F6 mute LED," and using it to reflect real speaker-mute state as-is
would incorrectly also light the mic-mute indicator.

**Read `SBKT` and `SMLS` directly (`.work/acpi-analysis-20260914/
ssdt2.dsl`) rather than keep guessing — this settles the mute-LED
question and rules out the flag theory:**

- **`SMLS` (set mute LEDs) always drives both LEDs in one call**, by
  design: it takes a single 2-bit argument (`LED2`, `LED3`), and
  unconditionally issues *four* possible `HQEX(0x06, ...)` writes — one
  each for LED2's on/off state and LED3's on/off state, every time it
  runs, regardless of which one actually changed. Windows always calls it
  with the *full* desired two-LED state, never one LED alone. Our driver
  models `platform::mute` and `platform::micmute` as two independent LED
  class devices and writes only one command per LED — a reasonable model
  that doesn't match how HP's own firmware treats them. **LED 8 lighting
  both physical LEDs together is the real, expected behavior of writing
  `0x06`/`0x08` in isolation, not a driver bug** — nothing this session
  can point to as "wrong" in the mailbox protocol itself. Fixing the
  1:1 assumption would mean reading `SMLS`'s actual bit layout
  (`LED2`/`LED3` in one byte) and matching it, or accepting the coupling
  and documenting it in the LED names/triggers instead.
- **The flag theory for the backlight is wrong.** `SBKT` is a plain,
  unconditional `HQEX(0x05, <level>, 0, 0)` — no preceding `HQEX(0x01,
  0x84, ...)` call, unlike `SMLS`. The driver's C code
  (`hpec_kbd_backlight_set()`) already matches this exactly: `HPEC_OS_FLAG`/
  `HPEC_OS_FLAG_LEDS` exist and are correctly used only for the LED path,
  never for the backlight. Byte-for-byte, the driver sends what `SBKT`
  sends.

**Live check: the write reaches the EC and is acknowledged — no
communication failure.** With root, wrote the LED directly
(`echo 1 > /sys/class/leds/hp::kbd_backlight/brightness`): the write
returned success, meaning `hpec_command()` saw `HQEX_STATUS_DONE`, not a
timeout. The backlight still didn't turn on and the readback stayed `0`.
So this isn't a broken I²C transaction either — the EC accepts and
acknowledges the exact command `SBKT` sends, and does nothing visible
with it.

**Searched for a missing prerequisite and didn't find one.** `MCMD=0x01`
(the "OS state flag" command family) has exactly seven sub-commands used
anywhere in HP's tables: `0x00`/`0x01`/`0x02` (cleared together by
`CLFG`, apparently at init/resume) and their "enable" counterparts
`0x80`/`0x81`/`0x82`/`0x84`, each behind its own named method (`APET`,
`SCET`, `MSET`, and `SMLS` for `0x84`). None of the three unlabelled ones
resolve to anything backlight-related by name or by what calls them —
whatever they gate, it isn't this. `0x05`'s own sub-command space also
has two other members besides the level (`0xFE` = the backlight
*timeout* setting, read/written by `SYKT`/`SKTR`; `0xFF` = the current
level, read from the EC's own `_WED` event 0x0D handler when the
hardware Fn-key toggle fires) — neither is a prerequisite gate either,
just adjacent features on the same command byte.

**Where this leaves it.** The command-table, the driver's byte-for-byte
match to `SBKT`, and the transport are all confirmed correct; the write
is genuinely accepted by the EC and has no visible effect anyway. That's
consistent with a firmware quirk specific to this pre-release
board/EC revision — matching the pattern already seen elsewhere this
session (charging negotiation collapsing, the battery-manager service
hang) more than a fixable driver bug. Resolving it further would need
either a live bus trace of Windows actually changing the backlight (to
see if it sends something genuinely different from `SBKT`'s bytes), or
just retrying on a later EC firmware revision if HP ships one.

**Not a hardware concern.** Nothing here indicates any risk to the
keyboard, its backlight, or the LEDs — the backlight simply didn't turn
on when commanded (a fully safe failure mode, confirmed at the protocol
level as a clean acknowledged no-op, not a bus error), and the LEDs did
exactly what was asked, just not in the 1:1 mapping assumed. Safe to keep
iterating on the command sequence.

## Kernel `-10`: corrections and what changed

A second reading of HP's tables, against the `-9` capture, corrects two
conclusions above.

**Command `0x05` sets the backlight timeout, not the level.** HP's BIOS
setting "Keyboard Backlight Timeout" (`WMID`, setting name in `NSTR`)
writes through `IC10.SKTR`, which sends `HQEX(0x05, n)` with n = 0 for
"30 sec", 1 for "3 min" and 2 for "Never" (Windows shows "Always"). That
is the same command and range `SBKT` sends. Reading `0x05`/`0xfe` returns
the same encoding (`SYKT`). So:
- the `-9` driver's backlight "levels" set the timeout. The readback
  (`0x05`/`0xff`, the level) stayed 0 because the backlight really was
  off; the EC was not ignoring the command;
- the test left the timeout at "30 sec", the value its restore step wrote.
  The EC keeps it in RAM; on the ACPI boot, `SYKT` copies the EC's
  current value into the BIOS setting when the EC region disconnects;
- nothing in HP's tables sets the backlight level. F5 does, inside the
  EC.

`-10` drops the `hp::kbd_backlight` LED and adds a `kbd_backlight_timeout`
attribute on the EC device (`30s`, `3min`, `always`).

**The "LED 8 lights both keys" result is not established.** In the `-9`
capture, `platform::micmute` read 1 before its own test turned it on: F9's
LED was most likely already lit (the EC keeps the LED state; see below)
when `platform::mute` was switched on, so "both" was F6 plus a stale F9.
`SMLS` sets each LED from its own bit, which fits two independent LEDs.
`check-ec.sh` now records both states and asks what is lit before
changing anything, then lights each LED alone.

**EC events and hotkeys.** `ECGE` (`ACPI0013`) has one `GpioInt`: edge,
active low, PDC pin 768, which `analyze-acpi-pdc.py` resolves to GPIO 66.
Its `_EVT` reads the event byte from EC register `0x05` (`IC10.INTR`),
writes 0 back, and dispatches (`IC10.EAPQ`):

| Event | Meaning in HP's AML | `-10` driver |
|---|---|---|
| `0x11` | F9 hotkey, WMI event 0x04 code `0x0270` | `KEY_MICMUTE` (hp-wmi maps `0x270` so) |
| `0x1e` | F11 hotkey, WMI event 0x1d code `0x21a8` | `KEY_PROG2` (hp-wmi's programmable key) |
| `0x0d`, `0x1d` | F5, backlight: the WMI backlight events | ignored; the EC runs it |
| `0x88` | Fn lock, WMI code `0x21ab` | ignored (hp-wmi ignores it too) |
| `0x30`–`0x38` | fan and thermistor notices, as on Qualcomm's reference EC | ignored |
| `0x0b` | "S4 Hot": HP's AML asks the OS to hibernate | logged as critical |

HP's AML never writes the reference "enable events" command (`0x35`), and
the driver does not either. F9 also sends the HID Mute usage F6 sends
(`docs/keyboard-hotkeys-2026-09-29.md`), so on F9 both a speaker-mute and
a mic-mute key reach userspace; `check-ec.sh` records both, with
timestamps, before anything filters one.

**Mute LED state across operating systems.** The owner wants the mute
states to carry across reboots and between Windows and Linux. The EC holds
the LED state, and the `-9` reading suggests it survives a restart; the
next test asks whether the last boot came from Windows and what was
muted there. The driver reads the LEDs from the EC and never writes them
at probe. There is no ALSA sound card on any device-tree boot yet, so
nothing can be muted. Once there is, the plan is a boot step that reads
`platform::mute`/`platform::micmute`, sets the ALSA switches to match, and
only then attaches the `audio-mute`/`audio-micmute` LED triggers, which
otherwise reset the LEDs to "not muted".

## Kernel `-10`, live test: backlight timeout confirmed, LED coupling disproven, hotkey line silent

`sudo bash ~/check-ec.sh` (`captures/2026-09-30-ec/ec-test-182811.txt`),
`sudo bash ~/check-usb.sh` (`captures/2026-09-30-ec/usb-test-183203.txt`).

**Keyboard backlight timeout: fully confirmed, both settings.** Set to
`30s`: F5 turned the backlight on, and after 45 s untouched it was off —
matches. Set to `always`: same test, after 45 s it was still on —
matches. Restored to `3min` afterward. The `-10` correction (command
`0x05` is the timeout, not the level) is now proven correct, not just
argued from ACPI tables.

**The "LED 8 lights both keys" result from `-9` was wrong, and now we
know why.** This boot started with `platform::micmute` already reading
`1` — the owner confirmed the prior session was Windows, with the mic
muted, and this was a restart, not a power-off. The EC's LED state
carries across reboots and across OSes, exactly as hoped. But the
initial visual check ("before any change, which LEDs are lit?") answered
**none** — the register said micmute was on, but nothing was visibly
lit. Then, with both explicitly commanded off, the readback still showed
`micmute=1` (stale) while the owner confirmed **none** lit visually —
the GET path can read stale/stuck values independent of true LED state,
at least once. The two real tests that matter:

- `platform::mute` on alone → owner: **only F6 lit.**
- `platform::micmute` on alone → owner: **only F9 lit.**

**Both LEDs are independent**, exactly as the driver originally modeled
them. The `-9` "both lit" observation was almost certainly F9's LED
already being on (residual Windows mic-mute state) at the moment F6 was
tested, not a real hardware coupling — `SMLS` sending both LEDs' state
in one WMI call doesn't mean the *hardware* can't address them
separately, it only means Windows always specifies both. State was
restored to match the real prior mute (`mute=0`, `micmute=1`) rather than
left in an arbitrary test position.

**The new EC hotkey event line produced no events.** `check-ec.sh`
watched `HP OmniBook 5 EC hotkeys` (the new input device from GPIO 66)
alongside the keyboard and consumer-control devices for 30 s while F6,
F9, F11, F5 and Fn were pressed in order. Only the generic keyboard HID
interface reported anything: one `KEY_MUTE` (code 113, HID usage
`0xC00E2`) — ambiguous between F6 and F9 as always — and one `LEFTCTRL
+F17` chord (codes 29+187, matching "Special key A" from
`docs/keyboard-hotkeys-2026-09-29.md`), likely F11 or Fn. **Nothing at
all came from the new `HP OmniBook 5 EC hotkeys` device** — not for F9
(expected `KEY_MICMUTE`), not for F11 (expected `KEY_PROG2`). Either the
EC's event line (`ECGE`/GPIO 66) isn't actually firing for these keys, or
the driver's dispatch of a fired event isn't reaching the input device.
Not yet diagnosed further; this is the main open item from this boot.

**A new, separate SPMI warning.** `pmic-spmi 2-0b: probe with driver
pmic-spmi failed with error -5`, with a full kernel `WARNING` backtrace
(`pmic_arb_check_chnl_status_v1`, "transaction failed (0x3)"). SID 11 is
the "identify-only" SPMI slave from `docs/eusb2-repeater-2026-09-30.md`
— nothing is linked to it, so this is consistent with "no PMIC actually
answers at that slave ID," now with a real bus-level error backing that
up rather than just silence. Harmless (nothing depends on SID 11
probing), but worth quieting later if this SPMI bus is touched again.

**The USB-C repeater retest still didn't happen.** Both `usb_0`/`usb_1`
show `partner=no` in this capture — nothing was plugged into a USB-C
port this boot. The repeaters still identify correctly (`parent PMIC
subtype 0x5f v2.0` on both), but whether they actually fix full/low-speed
enumeration remains unconfirmed live. Still the single most-needed test:
a mouse in a USB-C port on a boot that also runs `check-usb.sh`.
