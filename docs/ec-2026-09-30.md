# Embedded Controller on the Device-Tree Boot: September 30, 2026

The EC (fan, EC thermistors, keyboard backlight, HP hotkey plumbing) was
reachable only on the ACPI boot, where HP's AML drives it over `IC10`
(`docs/cpuidle-and-ec-bus-results-2026-09-26.md`). No device-tree boot
describes it, so none has fan speed or EC temperatures
(`docs/status.md`). This note derives the EC's command set from HP's
ACPI tables (read-only work on the private DSDT/SSDT in `.work/`) and adds
a driver and a DT node for kernel `-9`. Nothing here has run on the
laptop yet.

## Bus

| Fact | Value | Source |
|---|---|---|
| Controller | `\_SB.IC10`, QUP 1 SE 1 at `0xa84000` = DT `i2c9` | DSDT `IC10` `_CRS`, `glymur.dtsi` |
| EC address, speed | `0x76`, 400 kHz, 7-bit | `I2cSerialBusV2` connections `ECIC` (SSDT) and `UMPC` (DSDT) |
| Pins | GPIO 36/37, function 1, pull-up | `IC10` PEP entry (`TLMMGPIO`), = `qup_i2c9_data_clk` |
| Clock | `gcc_qupv3_wrap1_s1_clk` | `IC10` PEP entry |
| Transfer mode | GSI (GPI DMA), FIFO disabled by firmware | ACPI boot, 2026-09-26; DT `i2c9` uses `gpi_dma1` |
| Event line | `ECGE` (`ACPI0013` GED) GpioInt, GPIO 66 | DSDT `ECGE` |

## Two command sets on the same address

1. **Qualcomm's reference EC commands** (AML field `DVUM`): `0x05` (read
   the pending event, as in `qcom-hamoa-ec.c`), `0x20`–`0x37`, `0x43`
   ("who am I"), `0x44` (capabilities, 6 bytes). HP's AML defines neither
   `0x0e` (firmware version) nor `0x42` (thermal capabilities), which
   `qcom-hamoa-ec.c` needs at probe, and that driver exposes no fan speed
   or temperatures. It is not used.
2. **HP's mailbox** (AML field `ICCR`, method `HQEX`), which carries the
   fan, thermistors and keyboard backlight:
    1. read status (`0xef`, 1 byte) until `0x00`, at most 20 × 5 ms;
    2. for commands with a payload, write it to `0xee` (32 bytes);
    3. write the command and sub-command to `0xed` (2 bytes);
    4. read status until `0xe0`, at most 20 × 5 ms;
    5. for commands with a reply, read 32 bytes from `0xee`.

   Each register access is a plain I²C write of the register byte plus
   data, or a write of the register byte and a repeated-start read, as
   the GenericSerialBus `AttribBytes` access defines it.

## Commands used by the driver

| Function | Command, sub-command | Reply | HP's AML |
|---|---|---|---|
| Fan speed | `0xbc`, `0x03` | bytes 0–1, little-endian RPM | `FAN1._FST` |
| Thermistor 1–4 | `0x26`, `0x00` / `0x07` / `0x04` / `0x0a` | byte 0, °C; `0xff` = no reading | `TRFE`, via `IC10._DSM` function 6, `TZ31`–`TZ34._TMP` |
| Keyboard backlight level | `0x05`, `0xff` | byte 0, level 0–2 | `WMID._WED` event `0x0d` |
| Set keyboard backlight | `0x05`, level 0–2 | none | `WMID.SBKT` (HP WMI keyboard backlight) |
| Mute LEDs, read | `0x06`, `0xff` | byte 1: bit 0 = LED 8, bit 1 = LED 9 | `WMID.GMLS` (HP WMI command `0x61`) |
| Mute LED on or off | `0x01`, `0x84`, then `0x06`, `0x08`/`0x09` (+`0x80` for on) | none | `WMID.SMLS` (HP WMI command `0x61`) |

Notes:
- `TZ35`–`TZ37` (thermistors 5–7, sub-commands `0x03`, `0x02`, `0x06`)
  return `_STA` 0 on this laptop, so the driver leaves them out.
- The thermal zones name the thermistors only "EC thermistor 1" to "4";
  their locations are unknown, so the driver uses those names.
- HP's `_TMP` reports the byte × 10 plus 2730 in tenths of kelvin; Linux
  converts with 2732, which is why the ACPI boot showed 40.8 °C for a
  41 °C reading.
- The keyboard has a backlight with two brightness levels (the owner,
  2026-09-30), matching EC levels 0 (off), 1 and 2. Its Fn key and
  auto-off timer already work without the OS, run by the EC
  (`docs/keyboard-hotkeys-2026-09-29.md`).
- The F6 (speaker mute) and F9 (mic mute) key LEDs have no bit in the
  keyboard's HID LED map (`docs/keyboard-hotkeys-2026-09-29.md`). HP's
  mute-LED WMI methods drive them through the EC as LEDs 8 and 9, sending
  the OS flag `0x84` first each time. Which LED is which is not in the
  tables: the driver names 8 `platform::mute` and 9 `platform::micmute`
  as a hypothesis, and `check-ec.sh` asks which key lights. Both keys send
  the same HID Mute usage, so telling them apart in software would need
  the EC's event path, which the driver does not use yet.
- Commands deliberately not used: fan trip points (`0xbd`), thermal
  thresholds (`0x28`), the other OS-state flags (`0x01`), and the reference
  fan-override command (`0x30`). They change how the EC runs the fan.

## What kernel `-9` adds

- `patches/kernel/upstream/qcom-next/0004`: DT binding
  `hp,omnibook-5-16-bf1xxx-ec`.
- `patches/kernel/upstream/qcom-next/0005`: `hp-omnibook-5-ec` driver
  (`CONFIG_EC_HP_OMNIBOOK5=m`). At probe it reads the fan speed once and
  fails if the EC does not answer. It registers:
    - hwmon `hp_omnibook_ec`: `fan1_input` and `temp1`–`temp4`, read-only;
    - LED `hp::kbd_backlight`, brightness 0–2.
    - LEDs `platform::mute` and `platform::micmute` (EC LEDs 8 and 9),
      without a default trigger until the test says which is which.

  It sends no command beyond the table above, polls instead of using the
  event line, and leaves the fan to the EC.
- The USB-test DT (`-usb.dts`, the "GPU and USB-A test" GRUB entry)
  enables `i2c9` with the EC node and unreserves GPIO 36/37. The other DTs
  are unchanged.
- `scripts/linux/glymur-ssd/check-ec.sh` reports the result. It steps the
  keyboard backlight through its levels and lights each mute LED in
  turn, asking what is lit. If the driver
  did not bind, it repeats only the read commands above with
  `i2ctransfer` (including the mute LED state), plus the reference `0x43`
  and `0x44` reads that HP's AML uses.

## Safety valve

The driver is a module. If the EC bus misbehaves, boot with
`module_blacklist=hp_omnibook_5_ec`, or use the other DT entries, which do
not enable `i2c9`.
