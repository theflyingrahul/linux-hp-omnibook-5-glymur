# TPM: How Windows Reaches It, and What Linux Would Need, November 6, 2026

Issue #19. Read-only work: the `-18` kernel log, qcom-next `17bbb4b37bbc`,
the laptops tree, Patchwork (linux-integrity), and the installed Windows
drivers (`QcTrEE8480.sys`, its INF). Nothing was run against the TPM.

## The posted Linux driver does not fit this laptop's firmware

Qualcomm's "tpm: Introduce Qualcomm TPM driver" (Kuldeep Singh, v4,
2026-10-19, Reviewed-by Jarkko Sakkinen; in the laptops tree, not in
linux-next) passes raw TPM 2.0 commands to a trusted application in
Qualcomm's TrustZone, reached as QTEE service 81 (`qcom.tz.tpm`) over the
QCOMTEE object interface. It was tested on the Glymur CRD.

Our base already carries the service-discovery half of that series, and
every `-18` boot logs:

    qcomtee: QTEE version 5.2.0
    qcomtee: QTEE does not implement service 413.
    qcomtee: QTEE does not implement service 81.

Service 81 is the TPM and 413 the UEFI-variable app. HP's TrustZone
firmware does not offer either over the object interface, so the posted
driver would not bind here. (UEFI variables work anyway, through the older
QSEECOM interface and `upstream/qcom-next/0009`.)

## How Windows does it

- The "Trusted Platform Module 2.0" device is a child of a "Trusted Runtime
  Secure Service" (`{36DEAA79-C5DD-447C-95E6-B3859589291A}`) published by
  Qualcomm's TrEE driver (`QcTrEE_8480`, `oem102.inf`, driver
  685.13804.20) on the "Qualcomm System Manager Device" (`QCOM103E`).
- The INF defines that service as the TrustZone app **`qcom.tz.tpm`**,
  version 1.1, already resident (`SecureApp=1`, `LoadApp=0`): Windows looks
  it up by name, the same QSEECOM "app by name" mechanism Linux uses for
  `qcom.tz.uefisecapp`.
- The driver's TPM code (`TPMService.c`, TrEE 11.1.4) has a TPM type query
  (`QueryTpmType`), a discrete-TPM interrupt path
  (`InterruptServiceRoutineForDTPM`, `InitdTPMCallbackObject`), a listener
  callback (`TpmWaitListenerCallback`), the physical presence interface
  (`TpmServicePpi`) and a 5 s transfer timeout (`TpmTrfrTimeVal`).

So the transport Linux would need is the one that already works here
(QSEECOM, app by name), but the request format of `qcom.tz.tpm` and the
listener's role are not known yet; the posted driver's TPM command set
(version query, TPM type, send command with a raw TPM 2.0 buffer) is the
first guess for the payload.

## Would a Linux TPM driver disturb BitLocker?

BitLocker seals its key to PCR values measured during Windows' own boot.
PCRs reset at every reboot, so measurements made while Linux runs never
reach a Windows boot. What could matter is persistent TPM state: NV
indices, persistent objects, hierarchy authorizations, the dictionary-attack
lockout counter.

What the Linux kernel itself sends, with our configuration (`TCG_TPM=y`,
`TCG_TPM2_HMAC` off, `HW_RANDOM_TPM=y`, `IMA=y`):

| When | Commands | Persistent effect |
|---|---|---|
| probe (`TPM_OPS_AUTO_STARTUP`) | `TPM2_SelfTest`; `TPM2_Startup(CLEAR)` only if the TPM is not started (UEFI has already started it); `TPM2_GetCapability` (command table, PCR banks) | none |
| hwrng | `TPM2_GetRandom` | none |
| IMA at boot | `TPM2_PCR_Read`, `TPM2_PCR_Extend` of PCR 10 | none (PCRs are volatile; BitLocker does not use PCR 10) |
| shutdown | `TPM2_Shutdown(CLEAR)` | the TPM's normal orderly-shutdown save |

The kernel uses no authorizations, so it cannot raise the lockout counter,
and writes no NV indices or persistent objects. The risk is in userspace:
`tpm2_clear`, `tpm2_changeauth`, or tools that create persistent keys
(`systemd-cryptenroll` uses the storage root key at `0x81000001`, a handle
Windows also uses) must not be run without a separate decision.

Open: whether the app's listener stores TPM state through the host OS (as
the SPU does through `qcsp.sys`). If it does, a Linux boot with a missing
or different listener could break the TPM's state saving, which is a real
risk to BitLocker; that has to be read from `QcTrEE8480.sys` before any
command is sent from Linux.

## Where the TPM keeps its state (static analysis, 2026-11-06)

From `QcTrEE8480.sys` (SHA-256 `d29208a9…`, TrEE 11.1.4; LLVM disassembly,
no decompiler) and its registry parameters:

- The TrEE driver serves TrustZone through host-side listeners. It
  registers listener `0x2000` (RPMB, 128 KiB buffer) and `0x7000` (time),
  plus `0xa`, `0xb`, `0xc` and `0xd000`, and an OS service listener
  `0xc000` (`ListenerID = 49152` in the registry).
- Its file-system listener is on (`FSListener = 1`) and keeps TrustZone's
  files under `FileListenerPath = \DriverData`, that is
  `C:\Windows\System32\DriverData`, on the BitLocker volume.
- The TPM service depends on these: its connect routine (`0x140026390`)
  sends the TPM app "RPMB listener up" (`SendRpmbListenerUpSignal`), and
  the app setup for `qcom.tz.tpm` (`0x140020610`) asks whether the RPMB
  listener is installed (`QueryRPMBListenerInstallation`).
- The driver's RPMB code covers UFS and eMMC only (`UfsRpmbRead/Write`,
  `EmmcRpmbRead/Write`); this laptop has an NVMe drive. Whether the TPM's
  persistent state is in RPMB at all here, or in files through the
  file-system listener, is not established.

So the TPM app does not keep its state inside TrustZone alone; it relies on
the host OS for storage. Under Linux nothing serves those listeners, and if
the state is kept in files on C: (BitLocker), Linux cannot provide it at
all without touching the Windows volume, which is off limits.

Consequence: until it is known which listener holds the TPM's persistent
state, Linux must send the TPM no command at all, not even a read: a TPM
whose state cannot load or save could fail, or save a divergent state that
Windows then reads. That is a direct risk to BitLocker.

Static analysis cannot settle which store the TPM uses: that is decided
inside the `qcom.tz.tpm` app in TrustZone, and the app's binary is not in
the BIOS 15.06 capsule we have (its UEFI side, `fTpmDxe` with `Tcg2Dxe`,
`TcgMor` and `Tcg2PhysicalPresenceDxe`, is). The Windows driver's RPMB
query (`0x14002b8d8`) asks TrustZone about listener `0x2000`, which only
says the TPM path cares about RPMB. Remaining ways to find out, both on
Windows: the TrEE driver's own event trace (autologger
`{7F7D7CDE-1973-445F-B132-2B9544FEE9EC}`) during a TPM operation, which
needs an elevated session and the owner's go-ahead; or asking Qualcomm
(Kuldeep Singh's series) how their fTPM stores its NV on HLOS-listener
platforms.

## Plan

1. Reverse-engineer `QcTrEE8480.sys`'s `TPMService.c` statically: the
   request and response format sent to `qcom.tz.tpm`, the TPM type query,
   and which listener the TPM app uses for its persistent state (RPMB or
   the file-system listener). Started 2026-11-06; see above.
2. Only if the TPM's state does not depend on host storage Linux cannot
   provide: a test module that only looks the app up and asks its version
   and TPM type (no TPM command), default-off, for one boot. If the state
   lives in files on C:, stop here: a Linux TPM driver would need the
   Windows volume and is not pursued.
3. Only then a `tpm_qcom_qseecom` driver (a QSEECOM client like
   `qcom_qseecom_uefisecapp`), first tested with `tpm2_getcap` and
   `tpm2_pcrread` only. Upstream form: the same TPM command layer as
   Kuldeep Singh's driver, with the QSEECOM transport for firmware that has
   no QTEE service 81.

Nothing here writes to the TPM. Every step that sends a TPM command needs
the owner's go-ahead (BitLocker), as UEFI variable writes do.
