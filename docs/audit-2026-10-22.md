# Audit of the 2026-10-21/22 work (kernel `-16`)

A review of the commits and notes of 2026-10-21 and 2026-10-22, from the
`-16` plan through `ec-hotkey-flags.sh`, checked against HP's AML, the raw
logs in `captures/2026-10-21-runbook-16/` and the series. The dated notes of
those days are left as written; this note corrects them.

## The EC event register is `0x00`, not `0x05`

The EC driver (`upstream/qcom-next/0005`) read the pending event from
register `0x05`, and `docs/runbook-results-16-2026-10-21.md` says HP's AML
does the same. It does not. In HP's DSDT:

- `IC10.CMD5` is the only field of its `Field (DVUM …)` block, declared with
  `AccessAs (BufferAcc, AttribByte)` and no `Offset ()`, so it is command
  byte `0x00`. The name carries no offset.
- Every other byte-access field in `DVUM` gives its command with an explicit
  `Offset ()` that matches its name (`FC23` at `0x23`, `FC35` at `0x35`,
  `FC43` at `0x43`). Only the raw-access fields (`AttribRawBytes`,
  `AttribRawProcessBytes`) omit it, because they carry the command in their
  buffer.
- `IC10.INTR` reads `CMD5` into `BUF5` (status, length, data), writes `0`
  back to `CMD5`, and calls `IC10.EAPQ`, which dispatches on the data byte:
  `0x30` "Fan 1 status change", `0x31`–`0x34` the other fan and LUT
  notices, and so on (the full table is in `docs/ec-2026-09-30.md`, whose
  register number is wrong in the same way).
- The "`0x05`" came from the field name and from Qualcomm's reference EC
  driver (`qcom-hamoa-ec.c`), whose EC firmware is not HP's.

On the laptop, with the driver unbound, register `0x00` held `0x30`, HP's
fan notice, and writing `0` to it stopped the event line (GPIO 66) falling
every 118 ms. Register `0x05` read `0x00` throughout. So the line that fired
about nine times a second on `-16` was one fan notice that was never
acknowledged, and F9's event (`0x11` in HP's table) could not have been
seen.

`0005` now defines `HPEC_EVENT` as `0x00`. It is not built yet.

## The OS-state flag experiment is void

`ec-hotkey-flags.sh` set HP's OS-state flags (mailbox command `0x01`) while
watching register `0x05`, so its "no event" results say nothing. It also
cleared flag `0x80` at the end; `0x80` (`APET`) is the action-keys mode, and
clearing it left F1–F12 as plain function keys. The flags persist in the EC
and cannot be read back. The owner reset them with a BIOS reset on
2026-10-22. The script now watches and acknowledges `0x00`, leaves `0x80`
set, and asks for a typed confirmation before writing anything; EC writes
need the owner's go-ahead. `ec-event-capture.sh` no longer offers a pass with
the reference command `0x35`, which HP's AML never sends.

## Iris: the one-core patch is dropped

`upstream/qcom-next/0008` ("media: iris: add a one-core variant for Mahua")
made `-16` run Iris with one core. HP's firmware (`qcvss8480.mbn`) refused
it ("Configured core 0 is not supported") as it refused the two-core
configuration on `-15`. So the core count was not the problem, the patch
had no other evidence behind it, and it is removed. Iris is disabled again
in the test device tree; software decoding works.

## WirePlumber: the card name rule never applied

`boards/hp-omnibook-5-16-bf1xxx/audio/wireplumber/51-hp-omnibook-5-16-audio.conf`
matched the device on `alsa.card_name`. That rule never applied: on `-16`
the card kept "Built-in Audio" while the node rules (Speakers, Microphone
array) took. It now matches on the device's name,
`device.name = "alsa_card.platform-sound"`, as the node rules match on
theirs. Not installed on the laptop yet.

## Personal identifiers in the history

Logs committed from the laptop's Linux install carried the Wi-Fi and
Bluetooth MAC addresses, the root partition and filesystem UUIDs, the host
name and the USB stick's serial number. They were rewritten out of the whole
history on 2026-10-22 (`git filter-repo --replace-text`, rules kept
privately), commit references in messages and notes were remapped to the new
hashes, and `main` was force-pushed with the owner's approval. Afterwards:

- `scripts/linux/sanitize-capture.sh` masks MAC addresses, UUIDs, serial
  numbers and BitLocker labels in a log before it is committed, then lists
  anything identifier-like left over; `captures/README.md` requires it.
- `glymur-boot-report.sh` and `check-usb.sh` redact the same things as they
  write, and no longer print filesystem labels; `check-gpu-test.sh` masks
  `root=` in the command line.
- `build-qcom-next-glymur.sh` sets `KBUILD_BUILD_USER` and
  `KBUILD_BUILD_HOST`, so `uname -v` no longer names the build host.

GitHub may serve the old commits by hash until it collects them.

## Still open, or claimed without proof

- The battery manager backport (`backports/0023`) logged no state
  notifications in its one test; that it works is not shown.
- After the SoundWire bus idles, the speaker amplifiers take about 25 s to
  re-attach, so the first sound can be lost.
- Rebinding the EC driver (as both EC scripts do) loses its interrupt until
  the next boot.
- F9 on the corrected driver, and whether any OS-state flag gates it, are
  untested.
