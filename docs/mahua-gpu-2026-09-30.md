# Mahua GPU: Qualcomm Describes the Adreno X2-85 Separately, September 30, 2026

Qualcomm's posted Mahua GPU series corrected how this repository
understood the GPU. This note records the correction, and what kernel `-11`
and the new Mesa build carry because of it.

## The correction

Qualcomm's Adreno developers describe Mahua's GPU in their series
"drm/msm: Mahua GPU support" (Jie Zhang, posted 2026-09-25). It is not a
partial-slice part, and no partial-slice SKU is commercialized yet. The
GMEM fix (`upstream/qcom-next/0002`) is still valid for partial-slice parts
in general, but it is not what fixes this laptop.

## What Mahua is, per Qualcomm's own public statements

- The SoC: "Mahua is a derivative of Glymur SoC with the third CPU cluster
  disabled" (Gopikrishna Garmidi, Qualcomm, cover letter of "Mahua SoC and
  CRD DT support" v2, 2026-03-18; applied by Bjorn Andersson). The word is
  "disabled", so this does not say Mahua is separate silicon.
- The GPU: "a smaller variant of the Glymur GPU, with fewer slices and
  smaller internal memories, but it shares the same register layout"
  (Akhil P Oommen's Mahua GPU series, 2026-09-25). Qualcomm gives it its
  own name (Adreno X2-85; Glymur's is the X2-90), chip ID, GMU chip ID and
  GMEM size, and does not count it as a partial-slice SKU.
- Whether Mahua is a separate die or Glymur silicon with parts disabled is
  not published. Press reports from leaked engineering-sample IDs call it
  a separate 12-core die; that is unconfirmed.
- What matters for the driver is settled either way: Qualcomm's catalog
  describes this GPU as 3 slices with 15.75 MB of GMEM, and that is what
  the hardware behaves as.

## What was actually wrong

`glymur.dtsi` describes Glymur's GPU, the Adreno X2-90
(`qcom,adreno-44070001`), and `mahua.dtsi` does not override it in
qcom-next. Qualcomm's own Mahua CRD (`mahua-crd.dts`) inherits the same
description. So every Mahua board, ours included, ran its GPU with the
X2-90 catalog entry:

| | X2-90 entry (what ran) | Mahua X2-85 entry (the series) |
|---|---|---|
| Chip ID in the catalog | `0x44070001` | `0x44060000` |
| Chip ID after the slice count is folded in | `0x44070031` | `0x44060030` |
| Slices (`max_slices`) | 4 | 3 |
| GMEM | 21 MB | 15.75 MB |
| GMU chip ID | `0x8010100` | `0x80a0000` |
| GMU compatible | `qcom,adreno-gmu-x285.1` | `qcom,adreno-gmu-x285.0` |
| Speed bins | 388, 357, 284 | the same |

The GPU reported 3 active slices against the X2-90's 4, which looked like a
partial-slice X2-90; Qualcomm describes it instead as a GPU with 3 slices. The corruption (`docs/gpu-corruption-2026-09-30.md`) was the
X2-90's 21 MB of GMEM on a chip with 15.75 MB. Our GMEM patch computed
15.75 MB from the slice count, which is why it worked here, but for Mahua
it treated a symptom. The GMU was also told the X2-90's chip ID.

## What kernel `-11` carries

- `backports/0013` and `0014`: patches 3 and 5 of the series, unmodified
  apart from one context line:
    - `0013` "drm/msm/a8xx: Add Mahua GPU support" adds the catalog entry
      and renames `adreno_is_x285()` to `adreno_is_x285_family()`. qcom-next
      also applies the A830 clock-gating value there; the note in the patch
      records how the conflict was resolved;
    - `0014` "arm64: dts: qcom: mahua: Support GPU and GMU" sets the Mahua
      compatibles in `mahua.dtsi`, so every Mahua board gets them, as
      upstream will.
- Patches 1, 2 and 4 are not carried. They fix Glymur's GMU compatible and
  the bindings; nothing here builds against the bindings, and Bjorn
  Andersson asked for patch 1 to change in v2.
- `upstream/qcom-next/0002` (the GMEM patch) stays, with the expression
  parenthesized on one line: on this chip it now computes 15.75 MB / 3 × 3,
  the catalog value.

This is not in qcom-next, msm-next or linux-next as of 2026-09-30, so
carrying the posted series is the newest code there is. Drop both patches
when qcom-next picks the series up.

## Mesa

Mesa identifies the GPU by the chip ID the kernel reports. Mesa 26.2.3 (and
the 26.2 and staging/26.2 branches) know only `0x44070031`; Qualcomm added
`0x44060030` on main (`d09fa965`, "freedreno: Add chip-id support for
Adreno X2-85", 2026-09-25), not nominated for stable. With `-11`, Mesa
26.2.3 would reject the GPU and GNOME would fall back to software
rendering.

`scripts/linux/build-mesa-glymur.sh` therefore builds Mesa main, pinned to
`cec59b29` (2026-09-30) and fetched by commit hash, as package
`26.3.0-devel-cec59b29-1`. It knows both chip IDs, so it also works with
kernel `-10` (the "previous kernel" entry). Mesa main needs
`python3-yaml` and `python3-packaging` in addition. The `26.2.3-2` package
stays on the USB for rollback.

## To check on the `-11` boot

- `check-mesa.sh` reads what msm reports to Mesa (`MSM_GET_PARAM`):
  `CHIP_ID` should end in `44060030` (the speed-bin fuse 0x165 above it)
  and `GMEM_SIZE` should be `0xfc0000` (16515072 bytes, 15.75 MB);
- `dmesg`: the GPU binds as `44060030` (not `44070031`), with the GMU
  firmware loaded and no speed-bin error (fuse 357 is bin 2 in both
  entries);
- GNOME's About page shows the GPU, `check-mesa.sh` finds the hardware
  driver in every program and in GNOME Shell, and the desktop is clean;
- `glmark2` against `-7`'s 11570.

## Result on kernels `-11` and `-12` (2026-09-30)

`check-mesa.sh` on the test device tree with kernel `-12`
(`captures/2026-09-30-dwc3-crash/mesa-test-233617-kernel12.txt`):

- msm reports `CHIP_ID` `0x16544060030`: chip `0x44060030` with the
  speed-bin fuse `0x165` (357) above it, as Qualcomm's Mahua entry and
  Mesa main expect;
- `GMEM_SIZE` `0xfc0000`, 16515072 bytes, 15.75 MB;
- the GMU firmware loads (`v5.2.38`) and no speed-bin error is logged;
- GNOME Shell has Mesa main's `libgallium-26.3.0-devel.so` loaded, and
  EGL, GLX and Vulkan all report "Adreno (TM) X2-85";
- `glmark2` scores 10376, and the GPU clock sits at 1.35 GHz under load;
  the two `-11` boots scored 11006 and 10289. `-7`, with the X2-90 entry
  and the GMEM patch, scored 11570; `-6`, with the X2-90's 21 MB, scored
  29.

So Qualcomm's Mahua series works on this laptop, and Mesa main drives it.
The GMEM patch runs in the same kernel and, as expected,
changes nothing here: the catalog already says 15.75 MB.
