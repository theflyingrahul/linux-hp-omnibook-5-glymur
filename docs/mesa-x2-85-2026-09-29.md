# Hardware Rendering: Mesa 26.2 for the Adreno X2-85, September 29, 2026

On kernel `-5`, the GPU binds, loads its firmware and scales its clock
(`docs/gpu-bringup-run1-2026-09-29.md`), but the desktop still reports
"Software Rendering". This note traces that to Mesa and stages a newer one
beside Ubuntu's.

## Cause: Ubuntu 26.04's Mesa predates the X2-85

The journal of the GPU test boot shows both Mesa drivers rejecting the chip:

```
MESA: error: fd_pipe_new2:49: unsupported GPU id 0x0 / chip id 0x16544070031
TU: error: ... device (chip_id = 16544070031, gpu_id = 0) is unsupported
```

The 64-bit value is what msm returns for `MSM_PARAM_CHIP_ID`: the chip ID
`0x44070031` in the low 32 bits and the speed-bin fuse `0x165` (357) above
it. Checked against Mesa's `src/freedreno/common/freedreno_devices.py`:

| Mesa | `0xffff44070031` "Adreno (TM) X2-85" |
|---|---|
| 26.0 branch (Ubuntu ships 26.0.8) | absent |
| 26.1 branch | absent |
| 26.2 branch, tag `mesa-26.2.3` | present (`CHIP.A8XX`, `a8xx_gen2`) |
| main | present |

The `0xffff` in the upper half is Mesa's wildcard for the speed bin, so any
fuse value matches. In 26.2.3 both drivers handle generation 8 without an
opt-in variable:

- OpenGL: `freedreno_screen.c` maps generations 6, 7 and 8 to
  `fd6_screen_init`.
- Vulkan: turnip's `tu_device.cc` accepts generation 6, 7 or 8.

A side result: this laptop's speed-bin fuse is 357. The kernel catalog
(`a6xx_catalog.c`, `ADRENO_SPEEDBINS`) maps it to bin 2, which enables the
`glymur.dtsi` OPPs whose `opp-supported-hw` has bit 2 set: everything up to
1.70 GHz (`0x7`). 1.85 GHz (`0x3`) is for bins 0 and 1 only. The test DT's
1.35 GHz cap is therefore conservative; this part is binned for 1.70 GHz.

## The build

`scripts/linux/build-mesa-glymur.sh` builds Mesa **26.2.3** as a normal
user on an Ubuntu 26.04 aarch64 host. The WSL build host is the same
distribution and architecture as the laptop, so its output runs there
unchanged.

- **Source:** `https://archive.mesa3d.org/mesa-26.2.3.tar.xz`, SHA-256
  `1628058a…a81f`, matching `docs/relnotes/26.2.3.rst`.
- **Dependencies:** fetched with `apt-get download` against a private,
  refreshed copy of the package lists, and unpacked into a sysroot. No
  root, and the host's apt state is untouched.
- **Drivers:** `freedreno` (GL/GLES, gallium) plus `softpipe` as the
  software fallback, and turnip (Vulkan). The other options are
  `platforms=x11,wayland`, `glvnd`, GBM and EGL; `llvm=disabled`.
- **Prefix:** `/opt/mesa-glymur`, so Ubuntu's Mesa in `/usr` stays as it
  is.
- **Package:** only the runtime is kept (EGL, GLX and GBM libraries,
  `libgallium`, turnip, the loader JSON files and drirc). Meson's
  libarchive wrap fallback installed `bsdtar` and `libarchive.so`, which no
  driver links, so they are dropped. The script checks that no driver
  needs libarchive. Every remaining `NEEDED` library is a stock Ubuntu
  desktop library.
- **Staged:** `mesa-glymur-26.2.3.tar.gz` (10.5 MB, SHA-256
  `547d3ed3…cbb25`) on the USB in `glymur-tools/kernels/`, listed in
  `SHA256SUMS`.

The Vulkan ICD file names `/opt/mesa-glymur/.../libvulkan_freedreno.so`
absolutely, and GBM has its backend directory compiled in. The EGL vendor
file names `libEGL_mesa.so.0`, which `LD_LIBRARY_PATH` resolves. The
install logic and the wrapper, including `--desktop on`/`off`, were
exercised against a scratch prefix in WSL; nothing has run on the laptop
yet.

## Using it without replacing Ubuntu's Mesa

`glymur-ssd/install-mesa.sh` unpacks the build to `/opt/mesa-glymur` and
adds `/usr/local/bin/mesa-glymur-run`.

- **One program:** `mesa-glymur-run <program>` runs it with the new Mesa.
  It sets `LD_LIBRARY_PATH`, the glvnd EGL vendor file,
  `LIBGL_DRIVERS_PATH`, `GBM_BACKENDS_PATH` and `VK_DRIVER_FILES`.
- **Whole desktop:** `mesa-glymur-run --desktop on` writes the same
  variables to `~/.config/environment.d/90-mesa-glymur.conf`, which takes
  effect at the next login. `--desktop off` removes the file.
- **If the desktop fails to start after `--desktop on`:** log in on a text
  console (Ctrl+Alt+F3) and run `mesa-glymur-run --desktop off`, or delete
  that file.

## Also staged: cpufreq at boot

`glymur-cpufreq.service` runs `modprobe scmi-cpufreq` at boot, but only
when `/sys/firmware/devicetree/base/firmware/scmi/arm,no-completion-irq`
exists. That is currently the GPU test DT only. On ACPI, full and minimal
boots the unit is skipped, because loading the module there hangs the
laptop. Install it with `install-cpufreq-service.sh` (`--remove` undoes
it).

## Test

1. From "Ubuntu on SSD: ACPI, newest glymur kernel", run the USB's
   `install-from-usb.sh`. It skips the `-5` kernel if that is already
   installed, then installs the Mesa build, the cpufreq service and the
   Ubuntu test tools (`mesa-utils`, `mesa-utils-bin`, `vulkan-tools`,
   `glmark2-es2-wayland`).
2. Boot "device tree (GPU test)".
3. From a terminal on the desktop, run `bash ~/check-mesa.sh`.
    - It runs `eglinfo` (Wayland, GBM, surfaceless), `glxinfo` and
      `vulkaninfo` with the new Mesa.
    - It then runs about 50 s of `glmark2` and 1000 frames of `vkcube`,
      sampling the GPU clock (devfreq) during each run.
    - It ends with the kernel log for GPU faults or hangs.
    - Output goes to `~/glymur-logs/mesa-test-*.txt`.
4. If that renders, try `mesa-glymur-run --desktop on` and log in again;
   GNOME Settings' "About" should then name the GPU.

## Live test, September 29: real hardware acceleration confirmed; the desktop-wide switch does not

Ran `check-mesa.sh` twice on "device tree (GPU and USB-A test)" (kernel
`-5`); both runs agree (`captures/2026-09-29-mesa-x2-85/`). Per-program,
through `mesa-glymur-run`, this is genuine hardware rendering:

```
$ mesa-glymur-run eglinfo -B -p gbm
OpenGL core profile vendor: freedreno
OpenGL core profile renderer: Adreno (TM) X2-85
OpenGL core profile version: 4.6 (Core Profile) Mesa 26.2.3
...
$ mesa-glymur-run vulkaninfo --summary
Selected GPU 0: Adreno (TM) X2-85, type: IntegratedGpu
```

`glmark2-es2-wayland` (GBM path) scores 29, and devfreq's `trans_stat`
shows real transitions to 760 MHz and 1.35 GHz during the `glmark2`/
`vkcube` runs, not just idle at 310 MHz — the GPU is doing the work, not
just binding. `eglinfo -B -p gbm` and `-p surfaceless` both give the real
device; only `-p wayland` (and `glxinfo` through Xwayland) still say
`softpipe`.

That split is the whole story: `-p gbm`/`-p surfaceless` talk to
`/dev/dri/renderD128` directly, bypassing the compositor. `-p wayland` and
Xwayland are Wayland *clients* of gnome-shell, and inherit whatever
gnome-shell itself can accelerate. So the remaining "Software Rendering"
in GNOME Settings is specifically about gnome-shell's own Mesa, not
whether the GPU or the new Mesa build work — both are now proven.

**The desktop-wide switch (`mesa-glymur-run --desktop on`,
`environment.d/90-mesa-glymur.conf`) did not reach gnome-shell, twice:**
once after `sudo systemctl restart user@1000.service` (which also,
unexplained, deleted the `.conf` file it was supposed to be reading — the
owner recreated it and used `--desktop off` afterward once specifically to
stop the visible session churn that restart caused) and once after a full,
clean reboot with the file genuinely present at boot time. In both cases
gnome-shell's own `/proc/<pid>/environ` never contained the override
variables, even though `gnome-shell` does run as a proper systemd user
unit (`org.gnome.Shell@ubuntu.service`, under `user@1000.service`) that
should in principle inherit `environment.d` imports made when the manager
starts. Why that unit specifically doesn't pick them up is still open —
not yet tried: setting the variables directly with `systemctl --user
set-environment` and restarting only `org.gnome.Shell@ubuntu.service`
(much less disruptive than restarting the whole user manager, but still
visibly restarts the compositor and every open window).

**Bottom line:** GPU bring-up is now proven end-to-end — kernel bind, GMU,
devfreq, and now real accelerated rendering and compute through Mesa
26.2.3, reproducibly. Only GNOME's own compositor process remains on
software rendering, which is a desktop-integration gap, not a hardware or
Mesa-build problem.
