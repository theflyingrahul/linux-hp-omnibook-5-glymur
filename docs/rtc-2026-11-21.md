# The clock, November 21, 2026

Every device-tree boot starts at the same wrong time: 23:05:38 on
October 2. Nothing reads a hardware clock, so the clock starts from
systemd's floor for it (most likely its build time).
On `-23`, Ubuntu 26.04's chrony then fails its NTS handshakes. The time
servers' certificates look "not yet valid", so the clock stays wrong for
minutes after each boot (`docs/runbook-results-23-2026-11-21.md`).

The owner wants this fixed in the device tree, not by saving the time on
disk (`fake-hwclock`). This note covers what the firmware does, what has
been tried, and the one-boot measurement that `-24` makes.

## What Windows does

HP's DSDT gives Windows an ACPI time and alarm device, `\_SB.PRTC`
(`ACPI000E`, `_GCP` = `0x1F7`):
- `_GRT` (get time) reads 16 bytes from the `\_SB.ABD` GenericSerialBus
  region at offset `0x30200` (field `XRTD`, through `\_SB.PMGK`). Status is
  byte 0 and the length byte 1; the rest is the ACPI time buffer: year,
  month, day, hour, minute, second, milliseconds, time zone, daylight.
- `_SRT` (set time) writes the same buffer back. The wake-timer methods
  (`_GWS`, `_CWS`, `_STP`, `_STV`) use the neighbouring offsets
  `0x30210` to `0x30230`.
- ABD (`QCOM1045`) is Qualcomm's ACPI bridge to PMIC GLink on the ADSP.
  The ADSP firmware implements the clock. Battery and USB-C use other
  offsets in the same region (`0x10480`, `0x20100`).
- Windows keeps the time in local time (India Standard Time here;
  `RealTimeIsUniversal` is unset).

## What Linux has tried

| Route | Result |
| --- | --- |
| PMK8850 RTC with the UEFI offset (`qcom,uefi-rtc-info`), as the Zenbook A16 and QCB do (`-17`) | probe fails with `-ENOENT`: HP's firmware has no `RTCInfo` variable. `-23` confirmed that again: 13 variables under Qualcomm's GUID, none of them `RTCInfo`. Konrad Dybcio said on 2026-09-11 that Glymur machines have none. |
| Qualcomm's PMIC GLink RTC driver (`rtc-qcom-glink`, v1 in qcom-next, `-19` to `-23`) | the time request `0x68` times out, `0x67` gets no reply, and `0x65` acks with `0xffffffff`. HP's ADSP firmware does not offer that service. Windows' request (ABD offset `0x30200`) is a different interface, and Linux has no ABD driver. |

Upstream on November 21: no newer version of the GLink RTC driver (v2 is
from November 2), and no other Glymur RTC work.

## The device-tree route left

The PMK8850 RTC block (`rtc@6100`) has a free-running 32-bit seconds
counter. `rtc-pm8xxx` reads it with no offset source at all, and the RTC
core lets the device tree choose which device is `rtc0`. `rtc0` is the one
the kernel sets the time from at boot (`CONFIG_RTC_HCTOSYS_DEVICE`). The
ADSP has to keep wall time somewhere, so either:
1. it writes this counter itself: then the counter is the time, in UTC or
   local time. The fix is the node plus an `rtc0` alias, and
   `timedatectl set-local-rtc 1` if it is local time;
2. it keeps an offset: the likely place is the PMIC's SDAM, the
   non-volatile scratch memory that `rtc-pm8xxx` can take an `offset` cell
   from (as on the ThinkPad X13s). The fix is the node with that SDAM cell
   as its offset, plus the alias;
3. it keeps the offset in its own memory, which Linux cannot read. Then
   there is no device-tree fix, and a driver for the ABD time request is
   the next step.

## Kernel `-24`

The test device tree enables `pmk8850_rtc` read-only:
- no offset source;
- `qcom,no-alarm` (its interrupt goes to the ADSP);
- no `allow-set-time`;
- the alias **`rtc1`**.

It cannot set the system clock until the counter is known. If the counter
held some unrelated value, an `rtc0` alias would move the clock forward,
and NTS would fail the same way. The daily tree is unchanged.

`check-rtc.sh` reads, without writing anything:
- the RTC and alarm register blocks through the PMIC's debugfs regmap;
- the raw counter, twice;
- all sixteen SDAM blocks (`0x7000` to `0x7fff`) into a private file;
- a reference time: chrony's if it is synchronised, otherwise the `Date`
  header of a plain HTTP request.

It prints the counter minus UTC and minus IST, and every SDAM word that
brings the counter within an hour of either.

## What decides `-25`

- **The counter is within minutes of UTC or IST:** move the alias to
  `rtc0` and set Linux's local-RTC setting to match.
- **An SDAM word turns the counter into wall time:** add an `offset` cell
  on that word to the RTC node, and make the SDAM read-only in the device
  tree, so that Linux's 11-minute RTC sync cannot change Windows' clock.
- **Neither:** the ABD request, `0x30200`, is the way forward.
